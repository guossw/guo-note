## 一、前缀缓存是什么

大模型每次生成回答时，都要把你发过去的整段对话重新"读一遍 + 算一遍"。这部分输入 token 是要花钱、花时间的。

但如果这次请求和上次请求**开头一大段是一模一样的**，模型其实没必要重新算——直接把上次算好的中间结果拿来用就行。这就是**前缀缓存**：把已经算过的前缀部分存起来，下次命中就跳过重复计算。

::: tip 一句话理解
就像你抄课文，第一段已经抄过且没改过，下次重抄时直接翻到上次抄完的位置继续往下抄就行，不用从头再抄一遍。
:::

## 二、为什么能省钱

以 DeepSeek 为例，**缓存命中**的 token 计费只有新计算 token 的一小部分（约 1/10 左右）。所以同样是 10 万 token 的上下文：

- 全部新算：按原价 100% 收费
- 90% 命中缓存：只对剩下 10% 的新内容付原价，其余 90% 按缓存价

实际效果就是**输入 token 成本降到约 1/5**。

## 三、缓存是云端的还是本地的

::: warning 关键点
这里说的"前缀缓存"是指**模型服务方（云端）的缓存**，不是你本地硬盘上的缓存。
:::

- **云端缓存**：部署在 DeepSeek / 其他推理服务商的 GPU 节点上，缓存的是模型推理时算出的 KV Cache（注意力机制中的 Key/Value 张量）。这些数据体积大、读取频率高，只存在于推理服务侧。
- **本地缓存**：你本地客户端通常只缓存对话文本、用户配置等，不涉及模型内部的 KV 张量。

所以前缀缓存能不能命中，**取决于你用的是哪家 API、那家有没有开启缓存、缓存有没有过期**，跟你本地配置无关。

## 四、怎么知道缓存是否命中

常见几种方式：

### 1. 看返回的字段

DeepSeek 官方 API 的响应里带有缓存统计字段：

```json
{
  "usage": {
    "prompt_tokens": 10000,
    "prompt_cache_hit_tokens": 9200,
    "prompt_cache_miss_tokens": 800
  }
}
```

- `prompt_cache_hit_tokens`：命中缓存的 token 数
- `prompt_cache_miss_tokens`：未命中、需要新算的 token 数
- 命中比例 = `hit / (hit + miss)`

### 2. 看账单 / 延迟

- 命中越多，首字延迟（TTFT）越低
- 命中越多，输入 token 费用越低
- 如果账单明细里有"缓存命中 token"一项，直接看金额差

### 3. 自己埋点

把每次请求的 `prompt_cache_hit_tokens` 记下来，按会话聚合统计命中率。

## 五、什么操作会让缓存失效

**只要前缀内容有一个 token 不一样，从那以后的缓存全部失效。**

常见的"无意识破坏缓存"操作：

| 操作                      | 为什么破坏缓存                       |
| ------------------------- | ------------------------------------ |
| 重排历史消息顺序          | 前缀变了，后面的全部 miss            |
| 改写摘要 / 重新润色上下文 | 文本变了，token 序列就变了           |
| 注入当前时间戳、随机 UUID | 每次都不同，前缀直接错位             |
| 把系统提示词放在中间      | 系统提示词应该放最前面，保证前缀稳定 |
| 工具结果插到历史消息前面  | 改变了已有前缀                       |

::: tip 正确做法
系统提示词 → 不变的工具定义 → 不变的历史对话 → 新一轮用户输入。**稳定部分一律往前放，易变部分一律往后放**。
:::

## 六、Reasonix 的"只追加"规则

Reasonix 处理聊天上下文有个死规矩：

> **上下文只往后追加新内容，绝不修改、打乱已经写好的旧内容，输出格式固定不变。**

### 举个例子

假设一个会话已经进行了 3 轮：

```
[系统提示词 - 永不变]
你是 Reasonix，一个编程助手。

[工具定义 - 永不变]
read_file / write_file / run_command ...

[第1轮]
用户: 帮我读 config.mts
助手: <调用 read_file，返回内容>...已读取...

[第2轮]
用户: 给我加一个侧边栏项
助手: <修改 config.mts>...已完成...

[第3轮]
用户: 再加一个
助手: ...
```

**普通 Agent** 可能这样破坏缓存：

- 第 2 轮结束后，把"第 1 轮的工具返回结果"压缩成一句"之前读了 config.mts"
- 第 3 轮请求时，前缀变了 → 缓存 miss

**Reasonix** 的做法：

- 第 1 轮写进去的内容，第 2 轮、第 3 轮、第 100 轮**原样保留，不动一个字**
- 新内容一律**追加在末尾**
- 输出格式（JSON 结构、字段顺序）**固定不变**

所以第 N 轮请求时，前面 N-1 轮的内容完全没变 → 这部分全部缓存命中。

::: tip 效果
数小时的会话中，每次请求 **90% 以上从缓存重放**，输入 token 成本降到约 1/5。
:::

## 七、只追加处理的弊端

凡事有利有弊，"只追加不改写"同样有代价：

### 1. 上下文无限膨胀

不压缩、不改写 = 历史只会越来越长。一个会话跑几小时，上下文可能堆到几十万 token，迟早撞到模型上下文上限。

### 2. 命中率高但绝对成本仍可能上升

- 缓存命中省钱，但**缓存 token 本身也要钱**（虽然便宜）
- 当上下文堆到 20 万 token，即使 90% 命中，每次请求仍要为 2 万新算 token + 18 万缓存 token 付费
- 对超长会话，**总账单可能反而比"激进压缩 + 低命中率"更高**

### 3. 信息密度下降

旧内容里很多是"过程性垃圾"：工具调用日志、调试输出、中间错误。保留它们对模型理解当前任务没帮助，反而稀释了关键信息，可能**降低回答质量**。

### 4. 触发自动压缩后又会破坏缓存

- 自动压缩默认在上下文达到 **80%** 时启动
- 压缩 = 改写历史 = 前缀变化 = 缓存全部失效
- 阈值越低，越早压缩，**缓存复用率越低，摘要调用越多，成本越高**

::: warning 配置权衡
`reasonix config compact-ratio` 可在 **30%–85%** 之间调整：

- **调高（如 80%）**：尽量不压缩，缓存命中率高，但单次请求 token 多
- **调低（如 30%）**：早早压缩，上下文短，但缓存经常失效、还要为摘要调用额外付费

桌面端设置与此共用用户级配置；可用 `--local` 给某个项目单独覆盖。
:::

### 5. 不适合需要"回溯修正"的场景

比如用户说"我之前给的需求是错的，请把方案 A 改成方案 B"——理想做法是直接修改历史里的需求描述。只追加模式下只能再加一条"修正声明"，历史错误信息还在，模型可能被误导。

## 八、小结

| 维度         | 只追加策略             | 激进压缩策略          |
| ------------ | ---------------------- | --------------------- |
| 缓存命中率   | 极高（90%+）           | 低（前缀常变）        |
| 单次请求成本 | 低（多数走缓存价）     | 输入 token 少但走原价 |
| 长会话总成本 | 可能更高（上下文膨胀） | 通常更低              |
| 信息保真度   | 完整保留               | 可能丢失细节          |
| 信息密度     | 低（含大量过程性内容） | 高                    |
| 适用场景     | 长编程 / Agent 工具链  | 闲聊 / 问答           |

::: tip 核心权衡
前缀缓存的本质是**用空间换时间、用稳定性换便宜**。只追加策略把这点用到极致，代价是上下文无节制增长。何时压缩、压缩到什么比例，是每个 Agent 框架都要回答的问题。
:::
